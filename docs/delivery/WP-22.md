# WP-22 (TASK-019): Storage adapters, media upload and lookup endpoints

Status: in progress — implemented; final verification in progress, 2026-09-29.

- Approved baseline: D-019, v0.2 foundation with the proposed v0.3 admin implementation contract.
- Implementation authorization/source: user asked to continue M3 and M4 from the latest master on 2026-09-29.
- Requirement IDs and canonical files: CAT-008 and CAT-016 (CATALOG-ADMIN §3.8, §11); SEC-001/004/005; ADM-001/003; ADMIN-BACKEND §2 and §9; API-REFERENCE §3.2.
- Acceptance scenario IDs: AC-34 lookup portion, AC-42 handler authorization, AC-45 upload/serving portion. Attachment and publishing UI acceptance remains in subsequent work packages.
- User-visible outcome: authorized catalog staff can use the API to upload catalog images and edit lookup values. No media/list editor screen is claimed; those are WP-28.
- In-scope surfaces/modules: local/static storage adapters, streaming multipart byte cap, raster signature/dimension validation, SHA-256 deduplication, immutable serving, media metadata patches and pagination, lookup read/create/patch/reorder, row versions and transactional audit helpers.
- Dependencies and blocking questions: WP-19/20 staff authorization implemented on this branch; Q-024 blocks production storage and EXIF policy. The local driver rejects production even when explicitly selected.
- Explicit non-goals: production object storage, image processing/EXIF stripping, customer photo storage, catalog structure editors, suppliers, pricing, looks and publishing screens.
- Data/API/asset contracts: existing 0003 tables, camelCase admin DTOs, bounded JSON, origin checks and staff rate limits. Invalid images return 413/415; invalid fields return 422 with paths; stale rows return 409 with the current DTO. Codes are not patchable through the lookup API, including before publication, as specified by API-REFERENCE.
- Loading/error/empty/recovery behavior: empty lists return arrays; invalid uploads never create a media row; exact duplicate content reuses its media ID; media content is immutable and metadata changes use row versions.
- Authorization and privacy requirements: catalog.read for reads; catalog.write for mutations; same-origin checks; 300/min shared staff mutation limit plus 60/min upload limit. Audit values contain no contact or customer information. The store is for public catalog images only.
- Migration/compatibility implications: none beyond the M3 0004 migration. Static reference media keeps its 308 redirect; local raster responses add immutable caching, nosniff and restrictive CSP.
- Test fixtures: `tests/fixtures/media/synthetic-64.{png,jpg,webp}` are generated 64×64 solid squares (Pillow), containing no customer data. QR fixture belongs to TASK-018.
- Verification plan: actual handler calls for upload/deduplication, metadata conflicts and serving; malformed type/dimensions/body cap; lookup metadata, code locks, version checks and atomic reorder; full checks and browser regression suite.
- Actual verification evidence: `npm run check` passed with 274 tests in 28 files before the final media-header hardening review. Final checks are in progress; see TEST-EVIDENCE.md when finalized.
- Deviations and decision references: the shared row-version/audit helpers needed by WP-22 were introduced in `db/admin-mutations.ts` for reuse by WP-23. No product or architecture baseline changed.
- Remaining limitations: EXIF is not stripped (Q-024); production object storage is not installed; list/media UI and attachment/publish acceptance await WP-28 and WP-34. Uploaded files can be orphaned if the database transaction fails after file write; they have no public media ID and operational cleanup is future work.
- Changed files/commit: `codex/m3-m4-admin-catalog`, continued from master `c8819a5`; see storage, media, lookup and admin mutation modules, routes and `tests/media-lookup.test.ts`.
